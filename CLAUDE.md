# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Salu-Salo** is an Android app for sharing surplus food within a community to reduce food waste. Donors post surplus food with a photo, quantity, pickup location and expiry. Recipients browse the available listings and reserve part or all of the quantity for pickup. The UI uses ₱ and Philippine sample locations.

- **Kotlin + Jetpack Compose (Material 3).** Single `MainActivity`, single `:app` module, package `com.example.salusalo`.
- **Firebase Authentication.** Email/password sign-up, sign-in, password reset, password change and sign-out, plus Google sign-in through Credential Manager (`data/GoogleSignIn.kt`; server client ID `R.string.default_web_client_id` from `google-services.json`, never hard-coded). "Keep me signed in" (unchecked by default) is a device-only setting checked on a fresh start (`MainActivity.onCreate`).
- **Supabase.** Postgres (via PostgREST and RPCs), Storage, Realtime and (since §18) Edge Functions, through supabase-kt 3.5 on Ktor with the OkHttp engine (Realtime needs WebSockets, which the Android engine lacks). Images load with Coil 3 `AsyncImage`.
- **Supabase trusts Firebase via Third-Party Auth.** `data/SupabaseClientProvider.kt` sends the current Firebase ID token as the Supabase access token. Since §21, when getting the token fails with `FirebaseAuthInvalidUserException` (account disabled or deleted, sign-in revoked or expired) it signs out, and the app returns to Sign In; a network failure never signs out.
  - Every Firebase user needs the custom claim `role: authenticated`. Since §18 (merged into `master` through PR #13 on 2026-09-28, merge commit `b8aa7f9`) the app sets it up itself: `UserRepository.ensureSupabaseRole()` calls the Supabase Edge Function `set-firebase-role` (`supabase/functions/set-firebase-role/index.ts`) when the token lacks it. The developer's local Admin SDK script stays as a backup and is **not in this repo**; don't add it.
  - SQL checks tokens with `is_salusalo_firebase_jwt()`, which requires issuer and audience = Firebase project `salusalo`.
- **Storage.** The existing private bucket **`food-images`** holds listing photos. The private **`profile-images`** bucket holds profile photos, visible only to their owner. Since §21 a listing photo can be read only by its uploader and by people who may see, saved or chat about its listing (`can_read_food_image`). Since round 2 (`20261009`) both buckets accept only JPEG, PNG and WebP up to 5 MB (the app uploads `.jpg`, which supabase-kt sends as `image/jpeg`); orphaned files are listed by the read-only `supabase/tests/storage_orphans_query.sql`, never deleted automatically.
- **Maps (Phase 5 part 2, §15; passed on two phones and merged into `master` through PR #11 on 2026-09-28 (merge commit `255b0f8`)).** osmdroid 6.1.20 with OpenStreetMap's tiles from `tile.openstreetmap.org` (no API key). The tile source is one constant, `MAP_TILES` in `PickupMap.kt`. Tile usage policy: the app's own User-Agent (`SaluSalo/<versionName> (Android; com.example.salusalo)`), "© OpenStreetMap contributors" on every map, tiles cached in the app's cache folder (50 MB), at most 2 downloads at a time, no bulk or offline downloading, no storage permission; never call osmdroid's `Configuration.load()` (it replaces the User-Agent). The free servers suit testing and a small user base; before a large public release, consider a tile provider meant for apps, whose key would stay out of the repo like the Supabase keys. Location: `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION`, foreground only, asked for only when "Use my location", Nearby or Nearest is used, through the platform LocationManager (`LocationManagerCompat`; no location library).

## Commands

Run these from the repo root. Toolchain: Gradle wrapper 9.4.1, AGP 9.2.1, Kotlin 2.2.10, JDK 21, compileSdk 37, minSdk 24.

```bash
./gradlew assembleDebug                  # build debug APK (Windows: gradlew.bat assembleDebug)
./gradlew installDebug                   # install on a connected device/emulator
./gradlew testDebugUnitTest              # JVM unit tests
./gradlew testDebugUnitTest --tests "com.example.salusalo.ExampleUnitTest"   # single test class (or Class.method)
./gradlew connectedDebugAndroidTest      # instrumented tests (needs device/emulator)
./gradlew lintDebug                      # Android lint
```

- On the current Windows dev machine, `java` is not on PATH. The build verified on 2026-09-25 used PowerShell:
  `$env:JAVA_HOME = "$env:USERPROFILE\.gradle\jdks\eclipse_adoptium-21-amd64-windows.2"; .\gradlew.bat :app:assembleDebug --offline`
- `local.properties` is git-ignored and must define `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. Both become `BuildConfig` fields, and `SupabaseClientProvider` throws if either is blank. Never print, copy or commit their values.
- `app/google-services.json` (Firebase project `salusalo`) is committed.
- Release signing (round 2): `app/build.gradle.kts` reads an optional, git-ignored `keystore.properties` in the repo root (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`); without it release builds are unsigned. Never create, commit or print a keystore or its passwords. R8 is off on purpose (§22.1 #31); the app's keep rules go in `app/src/main/keepRules/`.
- Backup rules (round 2): `res/xml/backup_rules.xml` and `data_extraction_rules.xml` exclude only Firebase Auth's saved sign-in file, named from the app ID in `google-services.json`; update both if that ID changes.
- Database changes are SQL files in `supabase/migrations/`. They are applied **manually**, in filename order, in the Supabase SQL Editor (see `supabase/README.md`). There is no Supabase CLI config, and nothing in the repo shows which migrations the live project has.
- `supabase/functions/` (§18) holds the Edge Function `set-firebase-role`. It is deployed by hand from the dashboard editor with JWT verification off (`supabase/README.md`); there is no `config.toml`. Its tests run with Deno, which is not part of the Android toolchain: `deno test supabase/functions/tests/set-firebase-role-test.ts`.
- `admin/` (the web admin dashboard, §25) has no build step. Its checks: `for t in admin/tests/*.test.js; do node $t; done` (timeline, sign-in messages, data layer). Try it locally with `npx http-server admin -p 8080 -c-1`; deploy with `npx firebase-tools deploy --only hosting` (the developer logs in once with `npx firebase-tools login`). `admin/js/config.js` must exist (copy `config.example.js`).
- `supabase/tests/` holds checks to paste into the SQL Editor, **not migrations**. `phase4_live_safety_check.sql` tests the Phase 4 refusals on the live project and always ends with an error on purpose, which rolls back everything it did.

## Architecture

Paths below are relative to `app/src/main/java/com/example/salusalo/`.

**Navigation uses plain Compose state. There is no Navigation library and no DI.**
- `SaluSaloApp()` in `MainActivity.kt` holds `screen` (`welcome | signin | signup | forgot | home`).
  - It starts at `welcome` only until this phone has seen the welcome pages (`welcome_seen` in `salusalo_session`, or a saved `keep_signed_in`; since §17), otherwise at `signin`.
  - It runs Firebase sign-in, sign-up and reset, then (since §18) `UserRepository.ensureSupabaseRole()` and `UserRepository.loadOrCreateCurrentProfile()` before entering `home`. If either fails, it shows Sign In with the Firebase user still signed in and a dialog with Close and Try again (Try again keeps the name typed on Create Account). Since §21: when the profile can't be created because an earlier profile has the same email (`ProfileException.EmailInUse`), the dialog offers "Restore your profile?" (`UserRepository.relinkProfile()`, `relink_my_profile`; an unverified email is sent Firebase's verification email first). The signed-in profile is saved with `rememberSaveable` (`ProfileSaver`), so rotation, dark mode, font size and process recreation keep Home without repeating setup. A `FirebaseAuth.AuthStateListener` returns to Sign In with "Your session has ended. Please sign in again." when Firebase ends the session while Home is open; `logOut()` leaves Home before signing out, so a normal Log out shows no message. Round 3: the same listener keeps Firebase's UID as Compose state (`authUid`) and the setup `LaunchedEffect` is keyed on it, so a sign-in that finishes after a rotation still sets the account up; `openAuthenticatedHome()` runs one setup at a time (`setupJob`), and the name typed on Create Account (`signUpName`) is saved when the button is tapped.
  - Since §29 the loading screen (`StartupScreen`) also shows for at least `STARTUP_INTRO_MS` (1.2 s) whenever the app opens, signed in or not (`introDone`, saved, so rotation doesn't repeat it; since §30 counted from when the app opened, `introStartedAt`, so a rotation doesn't restart it). Since §30 Home is drawn only with a profile, so the fade-out after Log out doesn't redraw it for no one.
  - System Back on Home closes the app without signing out (since §17; before, it called `logOut()`); only Profile's Log out signs out. On Create Account and Forgot password Back goes to Sign In; on Sign In and the welcome pages it closes the app.
- `HomeScreen()` (also in `MainActivity.kt`) holds `page` (`home | all | messages | alerts | post | activity | profile`; the `recommended` page was removed in §11) plus the bottom bar.
  - Food details open as a full-screen `Dialog` (`FoodDetailsScreen`). Since round 3 the open listing is held by `FoodViewModel.openedListing`, so rotation keeps the page open.
  - It creates the ViewModels with `viewModel(key = "food-$profileId")` / `"reservation-$profileId"` / `"messages-$profileId"` / `"notifications-$profileId"` / `"saved-$profileId"`, so each account gets its own instances. They live in the Activity's `ViewModelStore` and are reused if the same account signs in again; `clearSession()` empties their lists when `HomeScreen` is disposed, but not for a configuration change such as rotation (since §21).

**Layers**
- `data/`: plain repository classes that use the `SupabaseClientProvider.client` singleton.
  - `UserRepository` finds or creates the caller's `users` row, keyed by `FirebaseAuth.currentUser.uid`. Since §18 `ensureSupabaseRole()` runs first: the cached ID token, then one refresh, and only if both lack `role: authenticated` the `set-firebase-role` Edge Function (`supabase.functions.invoke`, the Functions plugin) and another refresh; one setup at a time (a process-wide `Mutex`); any failure is `ProfileException.RoleSetupFailed` (the pure steps are `ensureRole()`, tested by `SupabaseRoleTest`). Never show or log the Functions exception (its text can include the URL). It also changes the name and photo through the profile functions (since §16 the name and bio together through `updateMyProfile`, the `update_my_profile_details` RPC), uploads photos to `profile-images` (a new `<uid>/profile-<millis>.jpg` each time, shrunk by `data/ProfilePhoto.kt`), and changes the password (reauthenticate, then update). `supabaseErrorText()` shows only a `RestException`'s short `error` text, never the full message.
  - `FoodRepository` handles `food_posts` and image upload: the feed (newest first; donor names, ratings and "Email verified" from `get_listing_donor_profiles` through `withDonorProfiles()`, one call per list, since §14), create with up to 4 photos (each shrunk to a 1600 px JPEG by `encodeListingPhoto()` in `data/ProfilePhoto.kt`), `updateMyFoodPost()` (the `update_my_food_post_with_pin` RPC since §15, with a null pin keeping the stored one) and delete (removes every photo, best effort). Since §17 a list's photos are signed in one request: `withSignedImageUrls(bucket)` / `signedUrls(paths)` (pure core `signPhotoPaths()`, tested by `PhotoSigningTest`). supabase-kt 3.5.0 can't read the batch answer when one path can't be signed, so any failure except cancellation falls back to one request per photo; never show or log that exception (it can contain signed URLs). Since §21 the feed leaves out listings whose `pickup_end` has passed, and `createFoodPost(id, …)` takes the form's listing ID and runs through `publishOnce()` (tested by `PublishOnceTest`): a listing already saved with that ID is returned without uploading, photos are uploaded with upsert to the same paths, and after a failed insert they are deleted only when the database refused it (a `PostgrestRestException` with a code other than 23505) or a check finds no listing; when that check fails too, `PublishUnconfirmedException`. The profile photo upload likewise re-reads the profile before deleting a new photo after an unclear failure. Round 2: `UserRepository.getCurrentProfileId()` looks the profile ID up once per Firebase account and remembers it for the process (a profile's ID never changes); repositories that need only the ID use it instead of `getCurrentProfile()`. `data/ProfilePhoto.kt` decodes photos with `photoSampleSize()` (sampled on the longer side, so a 12 MP photo decodes at 2016×1512; tested by `PhotoSampleTest`).
  - `SavedListingRepository` handles `saved_listings` (bookmarks), with each listing embedded. `withSignedImageUrl(bucket)` (one listing) and `withSignedImageUrls(bucket)` (a list, since §17), top-level functions in `FoodRepository.kt`, turn stored paths into 1-hour signed URLs. If signing fails, only that post loses its image; the list still loads. Saved Listings signs the visible covers in one batch and the covers of listings the user can no longer see in another.
  - `ReservationRepository` handles reservation RPCs and reads. Since §17 it loads only the listings its reservations reference, by ID (`isIn`, chunks of 100), signs their images in one batch, and adds donor names to the recipient's own reservations (for "Rate <name>"). Since §21 `createReservation(id, quantity, unitPrice)` calls `create_reservation_at_price` with the price shown, and `releaseReservation()` calls `release_reservation`.
  - `ReviewRepository` (§14): `submit_review`, `get_my_given_reviews`, `get_listing_donor_profiles`, `get_listing_donor_reviews`, `get_my_rating_summary`, `get_my_received_reviews`. `ReportRepository` (§14): `submit_report`. `UserRepository.syncEmailVerified()` reloads the Firebase user, refreshes the token when needed and calls `sync_my_email_verified`; `sendVerificationEmail()` sends Firebase's verification email.
  - `MessageRepository` (conversation RPCs, messages; since §30 a chat loads its newest 1000 messages, oldest first) and `NotificationRepository` (alerts, preferences). `realtimeInserts()` in `data/RealtimeInserts.kt` streams inserted rows through a Realtime channel (the column filter is optional since §13; RLS decides which rows arrive). Since round 3 it takes `onRejoined`, called each time the channel joins again after a lost connection (supabase-kt rejoins but never replays the rows inserted meanwhile; `rejoins()`, tested by `RealtimeRejoinTest`): the alerts, the inbox and the open chat reload quietly then. `MessageRepository.getMyResponseRate()` calls `get_my_response_rate`.
  - `StorageRepository` builds storage paths.
  - `PhoneLocation` (§15): permission checks and a single foreground lookup through `LocationManagerCompat` (fused on Android 12+, then network, then GPS; a position up to 10 minutes old for distances, a fresh fix for the pin; a fix worse than 100 m counts as approximate). It returns the position only to the caller; nothing is logged, stored or sent.

## Security and ownership rules (keep them)

- Identity comes only from the token: `FirebaseAuth.currentUser` in Kotlin, and `auth.jwt() ->> 'sub'` / `current_salusalo_profile_id()` in SQL. Never trust a user or profile ID passed in from the UI.
- **Listings change only by insert, `update_my_food_post`, `update_my_food_post_with_pin` (§15) and `remove_my_food_post`** (plus the reservation RPCs for quantity and status, and, since §25, `admin_remove_listing` for admins, which also never deletes). Clients have no DELETE on `food_posts` either; never add a DELETE grant or policy. `remove_my_food_post` deletes a listing nobody reserved, reported or started a chat about (since §30), and otherwise marks it `REMOVED`, cancels its open reservations and alerts their recipients. Never tell the donor that a listing was reported (reports are anonymous): the app's texts say only "removed". Clients have no UPDATE on `food_posts`; never add an UPDATE grant or policy. The function takes the caller from the token, locks the row, refuses other people's and expired listings, and never changes quantity, unit, status, donor, photos or `created_at`. New insert fields must be sent explicitly (no defaults in `NewFoodPost`).
- Listing photos must be in the uploader's own `<firebaseUid>/<postId>/` folder (checked by the `food_posts` insert policy too).
- **`saved_listings`:** own rows only (select, insert, delete; no UPDATE; nothing for `anon`); insert only for a listing the caller can see that is not their own.
- Donor names come only from `get_listing_donor_names()` (older builds) and, since §14, `get_listing_donor_profiles()` (names, the badge and the rating only, same visibility as the `food_posts` SELECT policy, through `caller_can_view_food_post`). If that policy changes, change both functions and the helper.
- **Reviews and reports change only through `submit_review` and `submit_report`** (§14), and, since §25, reports also through the admin functions (`admin_remove_listing`, `admin_dismiss_listing_reports`, `admin_dismiss_report`; notes in `report_notes`). Clients have no privileges at all on `reviews` and `reports`, not even SELECT; never add a grant or policy. The person rated is the listing's donor and the person reported is the listing's donor or the chat's other participant, both found on the server, never passed from the app. Other people's reviews and ratings come only through the names-only functions (never an email, UID, role, phone, photo path or user ID).
- **Reservations change only through the RPCs.** Clients have SELECT only on `reservations`.
  - The RPCs lock the `food_posts` row and update `quantity`/`status` atomically.
  - Never write `reservations` directly, and never adjust listing quantity or status from the app.
- The server enforces these rules; the UI mirrors them but the server stays authoritative:
  - No one can reserve their own post.
  - Only the recipient can cancel, and only while the reservation is `RESERVED`.
  - Only the post's donor can mark a reservation claimed, or (since §21) release it, and only while it is `RESERVED`.
- Donors see recipient **names only**, via `get_donor_reservations()`. Conversation participants see each other's **name only**, via `get_my_conversations()`. Do not widen `users` RLS.
- **Messages and alerts change only through the Phase 4 RPCs and triggers** (and, since §27, admins' announcements through `admin_send_announcement`). Clients have SELECT only on `conversations`, `messages` and `notifications`; never insert them directly. `notify_user()` must stay non-executable for clients.
- Client-created profiles are always `RECIPIENT` (enforced by RLS). The client never sets `role`.
- **`users` rows change only through `update_my_profile_name`, `set_my_profile_image`, (since §14) `sync_my_email_verified`, (since §16) `update_my_profile_details` (name and bio) and (since §21) `relink_my_profile`.** Clients have SELECT and INSERT only; never add an UPDATE grant or policy on `users`, and never let these functions change `role`, `email` or `firebase_uid`. The one exception, requested for audit #15: `relink_my_profile()` moves `firebase_uid` to the caller's own new Firebase UID, only after the user confirms "Restore profile", only when the caller has no profile, Firebase's signed token says the email is verified, and exactly one profile has that email; never make it automatic or accept a UID or email from the app. `email_verified` is set only from the token's claim, never from a value the app sends, and an insert always stores false.
- `profile-images` stays private and owner-only; a photo path must be inside the owner's Firebase-UID folder.
- Keep `food-images` private and display images through signed URLs. Upload only under the uploader's own Firebase-UID folder. Since §21 other people read a photo only through `can_read_food_image` (never widen it back to every signed-in token).
- **`set-firebase-role` (§18) only ever sets `role: "authenticated"`, and only for the caller of a verified Firebase ID token of project `salusalo`** (signature, issuer, audience and times checked in the function). Never let it take an account, a claim or a value from the request, set any other claim, or act for another user. Its service-account key stays only in the Supabase Edge Function secret `FIREBASE_AUTH_ADMIN_KEY`: never in the app, the repo, the docs or a log. The function never logs or returns a token, the key, a Google access token, Google's error body or more than the first 6 characters of a UID. Keep the service account's role limited to `firebaseauth.users.get` and `firebaseauth.users.update`.
- Never add a Supabase service-role key or Firebase Admin credentials to the app, docs or commits. No map API key either; if a tile provider with a key is ever used, keep the key out of the repo like the Supabase keys.
- **Location (§15).** The phone's location is used on the phone for distances, and is never sent to Supabase or stored. The one exception is "Use my location" on Post and Edit, which puts the pin at the phone's position; the donor then saves that pin with the listing, and the note says who sees it. Keep the location permission foreground only and ask only when the user taps "Use my location" or chooses Nearby or Nearest.
- **Function privileges (round 2).** Every new function in `public` must `revoke all … from public`, `revoke all … from anon` and `grant execute … to authenticated` (or nothing, for internal helpers and trigger functions). No function may be executable by `anon`.
- **Rate limits (round 2).** Keep the limits in `send_message` and `create_reservation` when redefining them; a new function that alerts another person should get a per-profile limit counted under an advisory lock.
- **Reservation limits (§24).** Keep the limit check and the rate limit when redefining `create_reservation`, and the price check in `create_reservation_with_hold`. `pickup_deadline` is set only by `create_reservation_with_hold`, never by the app. `expire_overdue_reservations()` stays non-executable by every client role; the Cron job calls only it.
- **Admin functions (§25).** Only `users.role = 'ADMIN'`, set by hand in SQL, may run the `admin_*` functions; each starts with `admin_require()` and takes the caller from the token only. Clients have no privileges on `report_notes`, `admin_audit_log` or `reports`; the audit log is insert-only through the admin functions. Admins remove listings with `admin_remove_listing` (never delete) and alert only with existing types; since §27 the app skips alert types it doesn't know, but builds before §27 fail on them, so a new type still needs every phone updated before its migration. The dashboard holds only the publishable key; `admin/js/config.js` is git-ignored; never add a service-role key to it.
- A schema or RLS change needs a **new** migration file plus a note in `supabase/README.md`. Tell the user it must be run manually.
