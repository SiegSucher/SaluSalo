## Project

**Salu-Salo** is an Android app for sharing surplus food within a community to reduce food waste. Donors post surplus food with a photo, quantity, pickup location and expiry. Recipients browse the available listings and reserve part or all of the quantity for pickup. The UI uses ₱ and Philippine sample locations.

- **Kotlin + Jetpack Compose (Material 3).** Single `MainActivity`, single `:app` module, package `com.example.salusalo`.
- **Firebase Authentication.** Email/password sign-up, sign-in, password reset, password change and sign-out, plus Google sign-in through Credential Manager (`data/GoogleSignIn.kt`; server client ID `R.string.default_web_client_id` from `google-services.json`, never hard-coded). "Keep me signed in" (unchecked by default) is a device-only setting checked on a fresh start (`MainActivity.onCreate`).
- **Supabase.** Postgres (via PostgREST and RPCs), Storage and Realtime, through supabase-kt 3.5 on Ktor with the OkHttp engine (Realtime needs WebSockets, which the Android engine lacks). Images load with Coil 3 `AsyncImage`.
- **Supabase trusts Firebase via Third-Party Auth.** `data/SupabaseClientProvider.kt` sends the current Firebase ID token as the Supabase access token.
  - Every Firebase user needs the custom claim `role: authenticated`. A trusted Admin SDK or Cloud Function sets it; that code is **not in this repo**.
  - SQL checks tokens with `is_salusalo_firebase_jwt()`, which requires issuer and audience = Firebase project `salusalo`.
- **Storage.** The existing private bucket **`food-images`** holds listing photos. The private **`profile-images`** bucket holds profile photos, visible only to their owner.
- **Maps (Phase 5 part 2, §15; passed on two phones and merged into `master` through PR #11 on 2026-09-28 (merge commit `255b0f8`)).** osmdroid 6.1.20 with OpenStreetMap's tiles from `tile.openstreetmap.org` (no API key). The tile source is one constant, `MAP_TILES` in `PickupMap.kt`. Tile usage policy: the app's own User-Agent (`SaluSalo/<versionName> (Android; com.example.salusalo)`), "© OpenStreetMap contributors" on every map, tiles cached in the app's cache folder (50 MB), at most 2 downloads at a time, no bulk or offline downloading, no storage permission; never call osmdroid's `Configuration.load()` (it replaces the User-Agent). The free servers suit testing and a small user base; before a large public release, consider a tile provider meant for apps, whose key would stay out of the repo like the Supabase keys. Location: `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION`, foreground only, asked for only when "Use my location", Nearby or Nearest is used, through the platform LocationManager (`LocationManagerCompat`; no location library).

## Commands

Run these from the repo root. Toolchain: Gradle wrapper 9.4.1, AGP 9.2.1, Kotlin 2.2.10, JDK 21, compileSdk 37, minSdk 24.

```bash
./gradlew assembleDebug                  # build debug APK (Windows: gradlew.bat assembleDebug)
./gradlew installDebug                   # install on a connected device/emulator
./gradlew testDebugUnitTest              # JVM unit tests
./gradlew testDebugUnitTest --tests "com.example.salusalo.ExampleUnitTest"   # single test class (or Class.method)
./gradlew connectedDebugAndroidTest      # instrumented tests (needs device/emulator)
./gradlew lintDebug                      # Android lint
```

- On the current Windows dev machine, `java` is not on PATH. The build verified on 2026-09-25 used PowerShell:
  `$env:JAVA_HOME = "$env:USERPROFILE\.gradle\jdks\eclipse_adoptium-21-amd64-windows.2"; .\gradlew.bat :app:assembleDebug --offline`
- `local.properties` is git-ignored and must define `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. Both become `BuildConfig` fields, and `SupabaseClientProvider` throws if either is blank. Never print, copy or commit their values.
- `app/google-services.json` (Firebase project `salusalo`) is committed.
- Database changes are SQL files in `supabase/migrations/`. They are applied **manually**, in filename order, in the Supabase SQL Editor (see `supabase/README.md`). There is no Supabase CLI config, and nothing in the repo shows which migrations the live project has.
- `supabase/tests/` holds checks to paste into the SQL Editor, **not migrations**. `phase4_live_safety_check.sql` tests the Phase 4 refusals on the live project and always ends with an error on purpose, which rolls back everything it did.

## Architecture

Paths below are relative to `app/src/main/java/com/example/salusalo/`.

**Navigation uses plain Compose state. There is no Navigation library and no DI.**
- `SaluSaloApp()` in `MainActivity.kt` holds `screen` (`welcome | signin | signup | forgot | home`).
  - It starts at `welcome` only until this phone has seen the welcome pages (`welcome_seen` in `salusalo_session`, or a saved `keep_signed_in`; since §17), otherwise at `signin`.
  - It runs Firebase sign-in, sign-up and reset, then `UserRepository.loadOrCreateCurrentProfile()` before entering `home`.
  - System Back on Home closes the app without signing out (since §17; before, it called `logOut()`); only Profile's Log out signs out. On Create Account and Forgot password Back goes to Sign In; on Sign In and the welcome pages it closes the app.
- `HomeScreen()` (also in `MainActivity.kt`) holds `page` (`home | all | messages | alerts | post | activity | profile`; the `recommended` page was removed in §11) plus the bottom bar.
  - Food details open as a full-screen `Dialog` (`FoodDetailsScreen`).
  - It creates the ViewModels with `viewModel(key = "food-$profileId")` / `"reservation-$profileId"` / `"messages-$profileId"` / `"notifications-$profileId"` / `"saved-$profileId"`, so each account gets its own instances. They live in the Activity's `ViewModelStore` and are reused if the same account signs in again; `clearSession()` empties their lists when `HomeScreen` is disposed.

**Layers**
- `data/`: plain repository classes that use the `SupabaseClientProvider.client` singleton.
  - `UserRepository` finds or creates the caller's `users` row, keyed by `FirebaseAuth.currentUser.uid`. It also changes the name and photo through the profile functions (since §16 the name and bio together through `updateMyProfile`, the `update_my_profile_details` RPC), uploads photos to `profile-images` (a new `<uid>/profile-<millis>.jpg` each time, shrunk by `data/ProfilePhoto.kt`), and changes the password (reauthenticate, then update). `supabaseErrorText()` shows only a `RestException`'s short `error` text, never the full message.
  - `FoodRepository` handles `food_posts` and image upload: the feed (newest first; donor names, ratings and "Email verified" from `get_listing_donor_profiles` through `withDonorProfiles()`, one call per list, since §14), create with up to 4 photos (each shrunk to a 1600 px JPEG by `encodeListingPhoto()` in `data/ProfilePhoto.kt`), `updateMyFoodPost()` (the `update_my_food_post_with_pin` RPC since §15, with a null pin keeping the stored one) and delete (removes every photo, best effort). Since §17 a list's photos are signed in one request: `withSignedImageUrls(bucket)` / `signedUrls(paths)` (pure core `signPhotoPaths()`, tested by `PhotoSigningTest`). supabase-kt 3.5.0 can't read the batch answer when one path can't be signed, so any failure except cancellation falls back to one request per photo; never show or log that exception (it can contain signed URLs).
  - `SavedListingRepository` handles `saved_listings` (bookmarks), with each listing embedded. `withSignedImageUrl(bucket)` (one listing) and `withSignedImageUrls(bucket)` (a list, since §17), top-level functions in `FoodRepository.kt`, turn stored paths into 1-hour signed URLs. If signing fails, only that post loses its image; the list still loads. Saved Listings signs the visible covers in one batch and the covers of listings the user can no longer see in another.
  - `ReservationRepository` handles reservation RPCs and reads. Since §17 it loads only the listings its reservations reference, by ID (`isIn`, chunks of 100), signs their images in one batch, and adds donor names to the recipient's own reservations (for "Rate <name>").
  - `ReviewRepository` (§14): `submit_review`, `get_my_given_reviews`, `get_listing_donor_profiles`, `get_listing_donor_reviews`, `get_my_rating_summary`, `get_my_received_reviews`. `ReportRepository` (§14): `submit_report`. `UserRepository.syncEmailVerified()` reloads the Firebase user, refreshes the token when needed and calls `sync_my_email_verified`; `sendVerificationEmail()` sends Firebase's verification email.
  - `MessageRepository` (conversation RPCs, messages) and `NotificationRepository` (alerts, preferences). `realtimeInserts()` in `data/RealtimeInserts.kt` streams inserted rows through a Realtime channel (the column filter is optional since §13; RLS decides which rows arrive). `MessageRepository.getMyResponseRate()` calls `get_my_response_rate`.
  - `StorageRepository` builds storage paths.
  - `PhoneLocation` (§15): permission checks and a single foreground lookup through `LocationManagerCompat` (fused on Android 12+, then network, then GPS; a position up to 10 minutes old for distances, a fresh fix for the pin; a fix worse than 100 m counts as approximate). It returns the position only to the caller; nothing is logged, stored or sent.
- `model/`: `@Serializable` DTOs, with `@SerialName` for snake_case columns.
  - `FoodPost`: its `displayImageUrl` is `@Transient` (a signed URL, never stored). `price` is per unit, 0 = free. `formatPeso()` and `reservationTotal()` (same file) format money with `BigDecimal.valueOf`; never use `BigDecimal(double)`.
  - `Reservation`, `ReservationDisplay`, `DonorReservationRow`.
  - `UserProfile` (with `emailVerified` since §14 and `bio` since §16).
  - `model/Review.kt` (§14): `ListingDonorProfile`, `RatingSummary`, `ReviewItem`, `MyReview`, `ReportTarget`, `ReportReason` (codes and labels per target), `ratingLabel()` ("★ 4.7 (12)"), `starsText()`. `FoodPost` carries the donor's rating and badge as `@Transient` fields (`donorRatingLabel`).
  - `Conversation`, `ConversationSummary`, `ChatMessage`, `ResponseRate` (`model/Conversation.kt`, with `parseTimestamp()`); `AppNotification`, `NotificationType`, `NotificationPreferences` (its `recommendations` and `pickupReminders` have no switch since §13; they stay so a save writes back the stored values).
- `viewmodel/`: `AndroidViewModel` + `StateFlow`.
  - `FoodViewModel` exposes `availablePosts` and `myPosts`.
  - `ReservationViewModel` exposes `myReservations`, `donorReservations` and `message`.
  - `FoodViewModel`: requests run one at a time behind a `Mutex`. A feed or My Listings load requested while another request runs is queued and runs right after it (My Listings first). A write (`createPost()`, `updatePost()`, `deletePost()`) waits for the running request instead of being dropped; a second write before the first has finished is ignored (`saving` is true meanwhile), and create and edit report their own result (`createError`, `editResult`).
  - `SavedListingViewModel`: `savedIds` for the bookmark icons (loaded once per profile when Home starts), `saved` rows for Saved Listings (reloaded when it opens), `toggle()` changes the icon at once and reverts it if the server refuses.
  - `ReservationViewModel`: requests run one at a time behind a `Mutex`; a refresh asked for meanwhile is queued, never dropped. A second write (reserve, cancel, claim, and since §14 a review) before the first has finished is ignored (`saving`). `submitReview()` reports only to the Rate page (`reviewResult`); `myReviews` (the caller's own reviews, by reservation) loads with the lists. `reserve()` reports only to the review page (`reserveResult`) and sends the optional note in the reservation's chat. `refresh()` loads My Reservations and My Donations independently (`loadFailed`).
  - `MessageViewModel`: inbox, the open chat (`active`, `messages`, live while open) and `send()`. `start(profileId)` (§13) loads the inbox when Home starts and keeps it live through one unfiltered `messages` channel: a thread's last message, order and unread count change in memory, and an unknown thread is fetched once. The Home chat badge is the sum of `unreadCount`; `HomeScreen` reloads the inbox quietly once when the app returns from the background.
  - `NotificationViewModel`: alerts, `unreadCount`, preferences. `start(profileId)` keeps alerts live for the session and re-sends the Realtime token every 5 minutes (Realtime does not refresh the Firebase token itself; this covers the whole client, so don't add a second refresh). `newAlerts` (§13) emits only alerts that arrive live; `HomeScreen` plays `AlertSoundPlayer` (`AlertSound.kt`) for them while resumed, unless it is a message of the open chat, the ringer is not normal, or the phone-level `notification_sound` setting (`salusalo_session`, kept across sign-outs) is off.
- UI: large files in the root package.
  - `MainActivity.kt`: auth screens, Home feed, `RecommendationCard`, `AvailableFoodCard`, `FoodDetailsScreen` with Reserve (it opens `ReservationReviewDialog`). Since §17 Home has pull to refresh (`PullToRefreshBox`, feed and phone position only), the profile circle (signed URL keyed on the stored path) and "About the filters"; details open a full-screen photo view.
  - `ListingPhotos.kt` (§17): `ListingPhoto` (a listing photo from its signed URL: a plain tile without a stored photo, "Image unavailable" when a stored photo can't be shown; never a sample picture) and `FullScreenPhotos`.
  - `ActivityScreen.kt`: tabs My Listings, My Reservations (open and cancelled), My Donations, Purchases (claimed, priced), Claims (claimed, free), and totals computed from claimed reservations. Since §14 a claimed record the account received has "Rate <name>" / "Change your review" (opens `RateDonorPage`; a sent review reloads the feed). It shows reservation results and errors in a "Reservation" dialog, and reloads the reservation lists when their tab is tapped.
  - `PostScreen.kt`: Create Listing and `EditListingDialog`; since §15 both have the pickup pin picker (a pin is required on Post; on Edit it can be added or moved, never removed).
  - `PickupMap.kt` (§15): `MAP_TILES` and the osmdroid setup, `PickupMap` (an `AndroidView` of a `MapView` that keeps drags for itself inside scrolling pages, with the attribution), `PickupPinPicker`, `rememberLocationFinder()` (asks for access only when called) and `openDirections()` (Google Maps link, then `geo:`).
  - `ProfileScreen.kt` and `ProfileSections.kt`: profile. Since §13 the bell opens Alerts (dot only when unread), the gear opens Settings, "Notifications" opens Notification Preferences directly, and Response Rate is real. Since §14 (passed on two phones on 2026-09-28) the rating, the Ratings & Reviews panel and page, the "Email verified" chip and the Verification page are real, and Trust & safety's Report a concern explains the Report buttons. Since §16 (Mika's PR #10) Profile has no bell; the pencil opens Edit Profile (name and bio), the gear opens the Settings hub (`ProfileSettingsUi.kt`), and Food preferences and Location & distance are saved on the phone per account (`DiscoveryPreferences.kt`) and turn Home's "Newest listings" row into "For your preferences".
  - `AlertScreen.kt`: real alerts (Phase 4).
  - `ChatScreen.kt`: `ChatScreen` (conversation dialog; since §14 a flag in the header reports the other person) and `MessagesScreen` (inbox, page `messages`; no Refresh button since §13).
  - `ReviewsAndReports.kt` (§14): `RateDonorPage`, `ReportPage` (reasons follow the target) and `ReviewRow`; it reuses `ActionPage`, `ActionCard` and `ActionButton` from `FoodActions.kt`.
  - `FoodActions.kt`: `FoodActionsDialog` (the pickup location and provider pages; since §15 the pickup location page shows the pin on a map with "Directions" when the listing has one; questions go to the real chat through the required `onMessage`; since §14 the Donor/Seller page shows the badge, rating and latest reviews and has "Report <name>") and `ReservationReviewDialog` (the "Review reservation" page, which becomes the "Reserved" receipt). Since §17 it also holds `EdgeToEdgeDialog` and `DarkSystemBarIcons()`, used by every full-screen dialog page with text boxes (`ActionPage`, the chat, Edit Listing, the Profile pages) so the keyboard's insets reach them.
  - **Much of the UI is still demo/placeholder data** (sample records, hard-coded names and locations, preview-only flows). The feed, listings (with donor names, details and photos), saved listings, reservations (with the review page and receipt), Activity, messages, alerts, notification preferences, the profile name and photo, the Profile claims and donations, (since §13) the response rate, (since §14) ratings, reviews, reports and the Email verified badge, and (since §15) the pickup pin, distances, Nearby and Nearest use Supabase or real data.

## Security and ownership rules (keep them)

- Identity comes only from the token: `FirebaseAuth.currentUser` in Kotlin, and `auth.jwt() ->> 'sub'` / `current_salusalo_profile_id()` in SQL. Never trust a user or profile ID passed in from the UI.
- **Listings change only by insert, `update_my_food_post`, `update_my_food_post_with_pin` (§15) and `remove_my_food_post`** (plus the reservation RPCs for quantity and status). Clients have no DELETE on `food_posts` either; never add a DELETE grant or policy. `remove_my_food_post` deletes a never-reserved listing, and otherwise marks it `REMOVED`, cancels its open reservations and alerts their recipients. Clients have no UPDATE on `food_posts`; never add an UPDATE grant or policy. The function takes the caller from the token, locks the row, refuses other people's and expired listings, and never changes quantity, unit, status, donor, photos or `created_at`. New insert fields must be sent explicitly (no defaults in `NewFoodPost`).
- Listing photos must be in the uploader's own `<firebaseUid>/<postId>/` folder (checked by the `food_posts` insert policy too).
- **`saved_listings`:** own rows only (select, insert, delete; no UPDATE; nothing for `anon`); insert only for a listing the caller can see that is not their own.
- Donor names come only from `get_listing_donor_names()` (older builds) and, since §14, `get_listing_donor_profiles()` (names, the badge and the rating only, same visibility as the `food_posts` SELECT policy, through `caller_can_view_food_post`). If that policy changes, change both functions and the helper.
- **Reviews and reports change only through `submit_review` and `submit_report`** (§14). Clients have no privileges at all on `reviews` and `reports`, not even SELECT; never add a grant or policy. The person rated is the listing's donor and the person reported is the listing's donor or the chat's other participant, both found on the server, never passed from the app. Other people's reviews and ratings come only through the names-only functions (never an email, UID, role, phone, photo path or user ID).
- **Reservations change only through the RPCs.** Clients have SELECT only on `reservations`.
  - The RPCs lock the `food_posts` row and update `quantity`/`status` atomically.
  - Never write `reservations` directly, and never adjust listing quantity or status from the app.
- The server enforces these rules; the UI mirrors them but the server stays authoritative:
  - No one can reserve their own post.
  - Only the recipient can cancel, and only while the reservation is `RESERVED`.
  - Only the post's donor can mark a reservation claimed, and only while it is `RESERVED`.
- Donors see recipient **names only**, via `get_donor_reservations()`. Conversation participants see each other's **name only**, via `get_my_conversations()`. Do not widen `users` RLS.
- **Messages and alerts change only through the Phase 4 RPCs and triggers.** Clients have SELECT only on `conversations`, `messages` and `notifications`; never insert them directly. `notify_user()` must stay non-executable for clients.
- Client-created profiles are always `RECIPIENT` (enforced by RLS). The client never sets `role`.
- **`users` rows change only through `update_my_profile_name`, `set_my_profile_image`, (since §14) `sync_my_email_verified` and (since §16) `update_my_profile_details` (name and bio).** Clients have SELECT and INSERT only; never add an UPDATE grant or policy on `users`, and never let these functions change `role`, `email` or `firebase_uid`. `email_verified` is set only from the token's claim, never from a value the app sends, and an insert always stores false.
- `profile-images` stays private and owner-only; a photo path must be inside the owner's Firebase-UID folder.
- Keep `food-images` private and display images through signed URLs. Upload only under the uploader's own Firebase-UID folder.
- Never add a Supabase service-role key or Firebase Admin credentials to the app, docs or commits. No map API key either; if a tile provider with a key is ever used, keep the key out of the repo like the Supabase keys.
- **Location (§15).** The phone's location is used on the phone for distances, and is never sent to Supabase or stored. The one exception is "Use my location" on Post and Edit, which puts the pin at the phone's position; the donor then saves that pin with the listing, and the note says who sees it. Keep the location permission foreground only and ask only when the user taps "Use my location" or chooses Nearby or Nearest.
- A schema or RLS change needs a **new** migration file plus a note in `supabase/README.md`. Tell the user it must be run manually.

## Development rules

- **Inspect before modifying.** Read the relevant Kotlin and SQL, and check every claim (including those in docs and handoff notes) against the code.
- **Make minimal, targeted changes** in the surrounding style. Do not reorganize the large UI files, remove demo UI or add libraries unless the task requires it.
- **Reuse existing patterns.**
  - Signed URLs: `withSignedImageUrls(bucket)` for a list and `withSignedImageUrl(bucket)` for one listing, in `data/FoodRepository.kt`; keep the 1-hour expiry and never log a URL.
  - Image with fallback: `ListingPhoto(imageUrl, hasPhoto, …)` (`ListingPhotos.kt`), with `FoodPost.hasPhoto`.
  - A full-screen dialog page with text boxes: `properties = EdgeToEdgeDialog`, `DarkSystemBarIcons()`, and padding for the status bar, the navigation bar and the keyboard (`FoodActions.kt`).
  - The pickup-start rule: `isPickupStartAllowed()` in `model/FoodPost.kt` (Post's check and "Check your listing").
- **Stay inside the phase the user asks for.** Do not redo Phases 1–4, and do not start Phase 6 until the user asks.
- **Keep `docs/PROJECT_STATUS.md` current** whenever work changes status. Never mark anything fixed or tested unless it actually was.
